### 2.3 Arquitectura — Win condition 20 oleadas

**Decisión**: reducir la run a 20 oleadas. El DEVASTADOR es el jefe final en wave 20 y su muerte activa la victoria. Justificación: la run larga (50 waves) era inalcanzable en playtests; nadie llegó a verle el DEVASTADOR.

#### Cambios en Constants.java

| Constante | Antes | Después | Notas |
|-----------|-------|---------|-------|
| `MINIBOSS_WAVE_INTERVAL` | 10 | — | Eliminado (era modulo) |
| `MINIBOSS_GUARDIAN_WAVE` | — | **10** | Nueva, wave exacta |
| `ARQUERO_MINIBOSS_WAVE` | 20 | **14** | Movido antes del Devastador |
| `FRAGMENTADO_WAVE` | 30 | **16** | Movido antes del Devastador |
| `DEVASTADOR_FINAL_WAVE` | 50 | **20** | ← Condición de victoria |

#### Progresión de bosses — run de 20 oleadas

```
Wave 10  → GUARDIAN (minijefe, shockwave)
Wave 14  → ARQUERO (minijefe, teleport + proyectiles)
Wave 16  → FRAGMENTADO (boss intermedio, 3 fases)
Wave 20  → DEVASTADOR 💀 → VICTORIA
```

#### Cambios en SpawnManager.java

- `spawnBossesForWave()`: cambiado de `waveCount % X == 0` a `waveCount == X` (spawn único, no loop infinito)
- `eliteTipo()`: rangos reajustados para 20 oleadas (`< 5 / < 10 / < 16 / ≥ 16`)

### 2.4 Análisis: DataManager (JSON) vs Constants

| Clase / Sistema | Solo JSON (DataManager) | Solo Constants | Ambos |
|----------------|------------------------|----------------|-------|

| `EnemyPool` | — | — | ✅ pool size = Constants; depth scaling = JSON |

| `SpawnManager` | — | ✅ waves, spawn rates | — |

**Conclusión**:
- **JSON es imprescindible solo en WeaponDropper** — los stats de armas (daño base, velocidad de ataque, afijos) vienen de `weapons.json`. Si se elimina, las armas de cofre no tienen datos.
- **JSON prescindible en EnemyPool** — el depth scaling se podría migrar a Constants.
- **JSON ya eliminado** de `CollisionManager` (immunity/resist lookups) e `InscripcionSismica` (stun immunity check). Estos lookups no afectaban al juego de manera visible y causaban llamadas JSON en el game loop.
- **Constants domina**: 236 referencias en 20 archivos.

### 2.5 DB — Restauración DAO simplificada

El esquema anterior tenía 6 tablas. Se simplificó manteniendo el patrón DAO:

**Tablas conservadas**:
- `run` — score, tiempo, nivel, personaje, mana, completada
- `run_kill` — kills por tipo de enemigo
- `run_arma` — armas + inscripciones equipadas
- `tipo_enemigo` — catálogo (necesario para run_kill FKs)
- `meta_tokens` — tokens meta-progresión

**Tablas eliminadas**:
- ~~`run_upgrade`~~ — ya no se guarda (demasiada complejidad, poco valor para TFG)
- ~~`run_reliquia`~~ — ya no se guarda
- ~~`tipo_upgrade`~~ — catálogo eliminado con su tabla

**`DBManager.guardarRun()`**: transacción única DAO → insert `run` + `guardarKills` + `guardarArmas`. Sin upgrades, sin reliquia.

**`getTop10()`**: via DAO, devuelve todas las runs (no solo las completadas).

> [!warning] DB existente requiere limpieza
> El archivo `kaosuarina.db` existente tiene el esquema antiguo. Si aparecen errores de columna al ejecutar, **borrar el archivo** `kaosuarina.db` del directorio de ejecución para que se recree con el esquema nuevo.

### 2.6 Bug fix — DEVASTADOR sin velocidad

**Bug**: `Enemy.activate()` case `DEVASTADOR` nunca asignaba `speed`. El campo `speed` no se resetea en `activate()`, por lo que el Devastador heredaba la velocidad del último enemigo que ocupó ese slot de pool. En muchos casos resultaba en `speed = 0` → el boss spawnaba 700u lejos del jugador y nunca se movía.

**Fix**: añadido `speed = Constants.DEVASTADOR_SPEED_P1;` al case DEVASTADOR.

```java
case DEVASTADOR:
    enemyId = "EN_BOSS_FINAL";
    speed = Constants.DEVASTADOR_SPEED_P1;  // ← AÑADIDO
    size = 80f;
    health = Constants.DEVASTADOR_HP;
    ...
```
